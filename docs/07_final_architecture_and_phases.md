# Final Architecture & Build Phases — Evidence-Guided Target Prioritization (ALS)

This tracks build progress as "Phases" — a build-order layer that sits alongside `01_final_architecture.md`'s Stage 1-9 numbering (phases span multiple stages; this is about sequencing work, not replacing the architecture's stage numbering).

**Design principle, unchanged throughout:** deterministic modules compute every number. The LLM/agent layer only narrates, proposes (for verification), or controls investigation sequencing — never final scoring.

### Discovery: Pathway (Reactome) Ingestion — a disease-agnostic target annotation, not per-disease evidence
Parallel finding to `docs/06_evidence_heterogeneity_discovery.md`'s evidence-heterogeneity discovery, surfaced while building the pathway ingestion client. The original assumption — "pathway evidence exists via `evidences()`, it's just never been queried" — was wrong in an informative way, confirmed live: grouping **every** real evidence row for all 5 genes (9,564 for SOD1 alone) by `datasourceId`/`datatypeId` shows **zero** pathway-like entries anywhere via `evidences()`. Pathway membership in OTP is not target-disease evidence at all — it's a disease-agnostic **target annotation**, exposed only via `Target.pathways` (type `ReactomePathway`: `pathway`, `pathwayId`, `topLevelTerm`), confirmed by introspecting the `Target` type directly.

Practical consequence: `get_pathway_evidence(ensembl_id)` takes no `efo_id` argument at all, unlike every other evidence-fetching function in `open_targets_client.py` — pathway "evidence" in this pipeline is gene-level (does this gene participate in any curated pathway at all), not disease-specific. This is consistent with, and explains in hindsight, why `dimension_scoring.py`'s `score_pathway_curated()` was always a fixed 1.0 for curated membership rather than a disease-relevance score — there was never a disease-specific signal to score. Real counts (SOD1: 3 including "Detoxification of Reactive Oxygen Species" — biologically on-point for a superoxide dismutase gene; FUS: 4; NEK1: 1; C9orf72: 0; TARDBP: 0) reflect each gene's genuine Reactome annotation, not a missing-data artifact — and directly resolved the mechanistic gap for SOD1/FUS/NEK1 while correctly leaving it in place for C9orf72/TARDBP.

Both consumers of pathway evidence — the fixed pipeline (`scripts/ingest_evidence.py`) and the autonomous investigation loop (`app/agent/investigation_tools.py::search_pathway_evidence`, `app/agent/pipeline_handoff.py`) — call the exact same `get_pathway_evidence()`/`_build_pathway_fields()` functions; no duplicate pathway-fetching or field-derivation logic exists.

### Phase 7 — Agentic Evidence Verification (Literature) ✅ DONE
Stage 5's "LLM proposes → deterministic rule layer verifies" design, applied specifically to literature evidence — the one source type with no structured comparability fields (`COMPARABILITY_FIELDS_BY_SOURCE_TYPE["literature"] == []`), so the structured classifier (Phase 3) can never see it (literature `EvidenceRecord`s never have `direction_on_trait` set, the only field that route filters on). Deliberately separate from Phase 8's investigation loop too — that decides WHAT to investigate; this decides whether two ALREADY-gathered literature excerpts conflict.

**Built:**
- **`app/ingestion/literature_text_client.py`** (did not exist — confirmed via search before building, per instruction). `get_abstract_text(pmid)` fetches real abstract text via NCBI's `efetch` API using the PMID already stored as `EvidenceRecord.source_record_id` for `dimension="literature"` rows (works for both OTP's `europepmc` rows and this project's own direct-PubMed rows — both carry a real PMID there).
- **`EvidenceRecord.abstract_text`** (new column) and **`ContradictionLog.status` / `.proposed_by` / `.verification_reason`** (new columns — did NOT already exist, checked the model directly before assuming). Added via a real, non-destructive migration (`scripts/migrate_add_literature_columns.py`, plain `ALTER TABLE`, DB backed up first) rather than dropping/recreating the DB — confirmed all 2,292 real evidence records and 5 targets survived the migration intact. Pre-existing `ContradictionLog` rows (0 of them, real — see Phase 9's "zero confirmed contradictions" finding) would have been backfilled to `status="confirmed"`, `proposed_by="structured_classifier"` had any existed.
- **`app/core/verification/literature_contradiction_proposer.py`** — the plain-text proposer, exactly as specified: `"Here are two excerpts about {gene}'s role in {disease}... Respond in exactly this format: CLASSIFICATION: <one word>\nREASON: <one sentence>"`, parsed with a plain regex, not JSON.
- **`app/core/verification/literature_contradiction_verifier.py`** — deterministic checks only (no LLM call): same `target_id` (pins gene+disease), both records genuinely `dimension="literature"`, both have real non-empty `abstract_text`, and the proposer's classification is literally `"CONTRADICT"`.
- **`POST /contradictions/target/{id}/run-literature`** — backfills missing abstract text (bounded: `LITERATURE_CONTRADICTION_MAX_RECORDS=5`, `_MAX_CANDIDATES=15` in `config.py` — comparing every real pair would mean ~24,000 LLM calls for SOD1 alone), proposes over every pair of the bounded set, verifies every `CONTRADICT` proposal, and only ever persists what's verified.

**Design lesson, confirmed empirically, exactly as hypothesized:** avoiding tool-calling entirely dodges Phase 8's 3 distinct failure modes (JSON corruption, a leaked `<|channel|>commentary` token, a phantom tool call). Every real call made during this build — 3 hand-written excerpt pairs plus ~20 real pairs over SOD1/C9orf72's actual literature evidence — returned a cleanly parseable `CLASSIFICATION: <word>\nREASON: <sentence>` response, zero parse failures, zero malformed output. `call_llm_plain()` (already built and validated during Phase 8, reused here rather than reimplemented) never passes a `tools` parameter at all, so there is no function-calling turn for the model to corrupt in the first place — the whole failure class Phase 8 hit doesn't exist here by construction, not because this model got luckier.

**A real correctness bug was found and fixed while testing this against real data, not simulated:** `literature_text_client.py`'s first version extracted `AbstractText.text` directly, which in ElementTree only returns text BEFORE the first nested child element. Real PubMed abstracts routinely wrap gene names in inline markup — PMID 36711601's real abstract opens `"Repeat expansions in the <i>C9orf72</i> gene are the most common genetic cause of ALS..."` (1,588 real characters) — and `.text`-only extraction silently truncated it to `"Repeat expansions in the"` (5 words), which the proposer then correctly flagged as unusable (`"Excerpt A is incomplete, so its content cannot be compared to Excerpt B"` — the model caught the truncation, the client didn't). Fixed with `"".join(el.itertext())` instead of `el.text`; verified live (1,588 chars recovered) and covered by 4 regression tests (`tests/test_literature_text_client.py`) using constructed XML fixtures reproducing the exact structure, not depending on NCBI's live data staying unchanged.

**A real design decision made while wiring the route in, caught before it became a bug:** logged contradictions do NOT reuse `classification="direct_contradiction"` (the structured classifier's taxonomy value). Checked first: `scoring.py`'s Consistency computation divides confirmed-contradiction counts by `comparable_pair_count()` over only `direction_on_trait`-labeled records, and literature records never have that field set — so literature pairs are not in that denominator today. Reusing "direct_contradiction" would have silently inflated the Consistency numerator with no matching denominator increase. Logged rows instead use a new, distinct `classification="literature_contradiction"`, which `CONTRADICTION_SEVERITY_WEIGHTS` has no entry for (defaults to weight 0.0) — real, logged, queryable, but deliberately inert for Consistency scoring until the denominator is extended to include literature pairs too. Named explicitly as follow-up work, not silently done.

### Phase 7 follow-up: `literature_contradiction` wired into Consistency scoring and the gap taxonomy ✅ DONE
When Phase 7 was built, `classification="literature_contradiction"` was deliberately kept out of `compute_evidence_consistency()`'s structured pair-count denominator (reusing `"direct_contradiction"` there would have silently corrupted the score — see Phase 7 above). That made the signal real and logged, but numerically inert. This follow-up wires it in — correctly, not naively.

**Formula/logic decision (step 2), checked before implementing rather than assumed:** structured contradiction pairs (`comparable_pair_count()`) are an EXHAUSTIVE count of every real direction-labeled pair within a source type; literature pairs are a deliberately bounded SAMPLE (`config.LITERATURE_CONTRADICTION_MAX_RECORDS=5`, so at most 10 pairs per target, regardless of how many real literature records exist). Pooling their raw counts into one shared denominator (the "just dump it in" approach the task warned against) would treat 10 sampled pairs as equivalent evidence weight to hundreds of real structured pairs, and — worse — would let merely *running* the literature check (even finding zero contradictions) dilute an existing structured penalty, since the denominator would grow with no matching numerator increase. Implemented instead:
- `evidence_profile.compute_evidence_consistency()` — UNCHANGED signature and formula (still the structured-only sub-score); now explicitly skips any `"literature_contradiction"` key if present in its input, rather than relying on it being absent.
- `evidence_profile.compute_literature_consistency(literature_contradiction_count, literature_pairs_evaluated)` — the SAME formula shape (`1 - weight*count/denominator`), applied to literature's own correctly-scoped denominator. `config.CONTRADICTION_SEVERITY_WEIGHTS["literature_contradiction"] = 1.0` (full severity, same tier as `direct_contradiction` — a confirmed literature contradiction already passed both the LLM proposer AND the deterministic verifier, so there's no softer "different population" sub-tier the way structured evidence has).
- `evidence_profile.combine_consistency_scores(structured_consistency, structured_pairs, literature_consistency, literature_pairs)` — a pair-count-WEIGHTED average of the two independently-computed sub-scores (not their raw counts pooled, not a plain average of the two scores). When either side has 0 pairs, this reduces to exactly the other side's score — so a target that has never had the literature route run for it scores identically to before this follow-up, by construction, not by a special case.
- **`literature_pairs_evaluated` is reproduced deterministically at scoring time**, not newly persisted: `POST /contradictions/target/{id}/run-literature` always selects the first `LITERATURE_CONTRADICTION_MAX_RECORDS` literature records (by id) with real abstract text; `app/api/routes/scoring.py` re-runs that exact same selection query against `EvidenceRecord.abstract_text` to recover the same pair count, avoiding a new persistence point for what's otherwise a re-derivable quantity.
- **Kept visible, not collapsed:** `PriorityScore.consistency_breakdown` (new column, migrated via `scripts/migrate_add_consistency_breakdown.py` — non-destructive `ALTER TABLE`, DB backed up first, all 2,292 real evidence records + 39 existing `PriorityScore` rows confirmed intact after) stores `{structured_consistency, structured_pairs, structured_contradiction_count, literature_consistency, literature_pairs, literature_contradiction_count}` as JSON, exposed via `PriorityScoreOut.consistency_breakdown` — same "don't collapse dimensions" principle as `dimension_breakdown`. `evidence_consistency` itself stays a single float (unchanged contract for the composite `priority_score` and every existing caller).

**Gap taxonomy decision (step 3), made explicitly:** YES — a target with confirmed literature contradictions but zero structured ones CAN trigger the `evidence_consistency` gap. No new gap type was added; the existing gap's trigger condition (`evidence_strength >= threshold AND evidence_consistency < threshold`) already covers this correctly once `evidence_consistency` itself is literature-aware. What changed: `TargetEvidenceSummary.literature_contradiction_count` (new field, default 0 — backward compatible) and `GAP_TEMPLATES["evidence_consistency"]`, which previously always blamed "methodological disagreement" unconditionally — now names both real counts (`"{methodological_count} methodological disagreement(s) and {literature_count} confirmed literature contradiction(s)"`), so the gap's own explanation is honest about which source actually drove it rather than always attributing it to the structured classifier.

  | SOD1 | 1.0 (unchanged) | 0.9999 (unchanged) | none (unchanged) |
  | C9orf72 | 1.0 (unchanged) | 0.8992 (unchanged) | mechanistic, modality, validation (unchanged) |

  Both show real `consistency_breakdown` now: SOD1 `{"structured_consistency": 1.0, "structured_pairs": 11026, "structured_contradiction_count": 0, "literature_consistency": 1.0, "literature_pairs": 10, "literature_contradiction_count": 0}`; C9orf72 the same shape with `"structured_pairs": 1`. Both `literature_pairs=10` because both genes' real `/run-literature` results (Phase 7 above) examined 5 records / 10 pairs and confirmed zero — exactly as expected, a real no-op, not an untested assumption.

### Labeling distinction: `investigation_coverage` (added after the SOD1 finding above)
The SOD1 disagreement above — investigation loop reports 2 real gaps (modality, validation) that the fixed pipeline reports as zero, purely because the agent explored 3 of 4 dimensions instead of all 4 — is exactly the kind of result that could be silently misread as "the investigation loop found problems the fixed pipeline missed" rather than "the investigation loop simply didn't look at clinical evidence this run." To make that distinction impossible to miss, every gap-analysis response now carries an `investigation_coverage` label plus a `dimensions_not_explored` list:
- `app.core.gaps.gap_taxonomy.describe_investigation_coverage(explored_dimensions, verb)` — shared by both callers, not reimplemented per-path.
- Fixed pipeline (`POST /gaps/target/{id}/run`, `GapAnalysisOut` schema): always `"complete (4/4 dimensions queried)"`, `dimensions_not_explored: []` — it queries all 4 MVP dimensions unconditionally by design.
- Investigation loop (`app.agent.pipeline_handoff.score_investigation_result()`): derived from which tools the agent actually called this run (`InvestigationResult.gathered_evidence`'s keys — a tool called with zero rows still counts as "explored", unlike one never called). The real re-run above now reports `"partial (3/4 dimensions explored: genetic, literature, pathway)"`, `dimensions_not_explored: ["human_clinical"]`.
- `app/core/narration/agent_narrator.py`'s SYSTEM_PROMPT requires the model to append an explicit caveat naming the real `dimensions_not_explored` values whenever `investigation_coverage` is partial (`generate_investigation_narrative()`, fed by `build_investigation_grounding_data()`) — grounded in the real value passed through from `score_investigation_result()`, never invented by the model.
- Covered by `tests/test_investigation_coverage.py` (6 tests): the fixed pipeline's route via a real `TestClient` call always returns "complete"; `score_investigation_result()` returns the correct partial/complete label from constructed `gathered_evidence`; the narrator's system prompt and prompt payload both carry the real partial value through to the (mocked) LLM call.

**Two real issues found, not yet fixed:**
1. **`agent_reasoning` is empty at every intermediate step** in `InvestigationTrace` — only the final summary message contains real reasoning text. This undermines the auditability goal (proving *why* the agent chose each tool, not just *what* it called). Needs a prompt fix so the model states brief reasoning before each tool call.
2. **3-run comparison produced identical results across all 3 runs** — need to confirm whether `temperature=0` is set. If so, this is expected deterministic behavior, not evidence of "consistency under autonomy" — relabel honestly, or re-run with a non-zero temperature (e.g. 0.3-0.5) for a genuine variability test.

**Not yet checked:** whether the 0.9998 priority score for SOD1 is driven by genuinely strong individual evidence scores or a scoring artifact — pull the top 5 raw genetic evidence scores feeding the harmonic sum to confirm.

**Case-based comparison against published ALS research (case-based validation — small, hand-picked, biologically-informed examples, explicitly NOT statistical validation across a benchmark set):**

**SOD1 — agrees, with one caveat worth stating precisely.** The system reports zero gaps and near-1.0 priority, driven by real pathway evidence (Reactome: "Detoxification of Reactive Oxygen Species" — mechanistically on-point for a superoxide dismutase gene) and real clinical evidence: all 10 human_clinical rows carry `intervention=tofersen`. This matches the real, published record — tofersen (Qalsody) received FDA accelerated approval in April 2023, the first ALS treatment targeting a genetic cause ([Biogen](https://investors.biogen.com/news-releases/news-release-details/fda-grants-accelerated-approval-qalsodytm-tofersen-sod1-als), [ALS Association](https://www.als.org/blog/tofersen-approved-sod1-als)). **The caveat:** that approval was accelerated, based on a biomarker (plasma neurofilament light) surrogate — the pivotal trial's clinical-outcome endpoints did not reach statistical significance ([FDA label](https://www.fda.gov/media/186135/download)), and confirmatory trial data is still pending. The system doesn't parrot this as a flat 1.0: human_clinical's dimension score is 0.9803 (near-maximal, not literally maximal), reflecting OTP's own phase/precedence-based scoring across the 10 rows rather than treating "an approved drug exists" as automatically perfect evidence — a real, if subtle, point of alignment, not a coincidence. One more honest note: 2 of SOD1's 3 real Reactome pathway hits ("Platelet degranulation", "JAK-STAT signaling after Interleukin-12") are not obviously ALS-mechanistic — pathway evidence in this pipeline is disease-agnostic gene annotation (see Phase 2's discovery section), so "no mechanistic gap" means "this gene participates in *some* curated pathway," not "this specific pathway explains its ALS role." The mechanistic-gap rule is honest about what it checks; a reader of the raw pathway list should be too.

**C9orf72 — partially agrees, and the divergence is real, not cosmetic.** Published research is unambiguous that the GGGGCC hexanucleotide repeat expansion in C9orf72 is the single most common genetic cause of ALS/FTD, discovered in 2011, acting through several documented mechanisms — RNA foci, dipeptide-repeat protein toxicity, and loss-of-function haploinsufficiency ([PMC10838790](https://pmc.ncbi.nlm.nih.gov/articles/PMC10838790/)). The system's genetic dimension score (0.8273) is high and directionally consistent with that. But inspecting the real underlying rows shows *why* the mechanistic/validation gaps are flagged is more nuanced than "C9orf72 is under-characterized":
  - *(Numbers in this bullet are pre-fix — see "Post-fix re-verification" below for the corrected 0.9084/15-row figures; the argument itself is unaffected.)* Of C9orf72's 14 real genetic rows, only 2 come from ClinVar (`eva`) with a clinical-significance call; the other 12 are `gwas_credible_sets` L2G scores. This is a legitimate thing for the system to be uncertain about — it correctly reflects a genuine data-representation limitation, not a modeling error.

OTP's `clinical_precedence` datasource apparently hasn't indexed either program against this target-disease pair in our ingested snapshot — plausibly because these are RNA-targeted ASOs rather than the small-molecule/ChEMBL-style entries that datasource is built around, not because no trial exists. **Net read:** the *substance* of the validation gap (no proven clinical benefit yet for C9orf72) is correct — both real trials failed — but the system's rationale text ("no human/clinical evidence present") overstates the absence in a way a reader unfamiliar with the underlying data source could misread as "C9orf72 has never been tried in humans," which is false. ### Data-provenance wording fix (follow-up to the C9orf72 finding above)
`GAP_TEMPLATES["validation"]` and `GAP_TEMPLATES["modality"]` (`app/core/gaps/gap_taxonomy.py`) both stated absence as flat fact ("no human/clinical evidence is present" / "no existing compound in ChEMBL/DrugBank") — both are read from `clinical_precedence`, a real OTP datasource built around ChEMBL/DrugBank-style small-molecule entries (see docs/06), and both would miss a real RNA-targeted ASO or gene-therapy program exactly the way they missed BIIB078/WVE-004 for C9orf72. ### Genetic evidence: datatype-driven fetch (RESOLVED — Option A, confirmed feasible and implemented)
Fixes finding #1 above. Two options were on the table: query by OTP's real "datatype" grouping instead of a hardcoded datasourceId list (Option A — the actual generalization fix), or fall back to moving the same hardcoded list into `config.py` with a documentation warning (Option B — a mitigation, not a fix). **Checked Option A live before deciding, as instructed — it's genuinely feasible, just not in the naive form first assumed:**

- **Live schema introspection** of `Target.evidences` shows it accepts only `efoIds` / `datasourceIds` / `size` / `cursor` as arguments — **no server-side `datatypeIds` filter exists.** So a single query can't ask OTP "give me all genetic_association evidence" directly.
- **But** every real `Evidence` row carries its own `datatypeId` field (confirmed via introspection of the `Evidence` type), and grouping SOD1's real evidence by `(datasourceId, datatypeId)` showed a clean mapping: `genetic_association` → `eva`, `gwas_credible_sets`, `orphanet`, `uniprot_variants` (a **superset** of the old hardcoded 3-item list — `orphanet` was real and previously missing entirely); `clinical` → `clinical_precedence`; `literature` → `europepmc`; `animal_model` → `impc`.
- **A naive "fetch broadly, filter client-side" approach was tested and found unsafe:** an unfiltered `size=500` query for SOD1 (real total 9,564 rows across all datatypes) captured only 228 of the real 361 `genetic_association` rows — OTP's default row ordering interleaves datatypes, so a size cap silently truncates just like the old per-datasource cap did, in a new form.
- **What was actually implemented** (`open_targets_client.get_evidence_by_datatype()`, `_discover_datasource_ids_for_datatype()`): a two-step, fully-paginated fetch — (1) paginate through ALL evidence for the target-disease pair requesting only the lightweight `datasourceId`/`datatypeId` fields, collecting the real, complete set of datasourceIds under the requested datatype (cursor pagination confirmed working live: distinct pages, no overlap beyond coincidental field-value repeats); (2) issue a second, fully-paginated fetch using OTP's real, reliable `datasourceIds` filter with that discovered list. Verified live for SOD1: returns exactly 361 rows across `eva`(275)/`uniprot_variants`(83)/`gwas_credible_sets`(2)/`orphanet`(1) — matching the independently-measured ground truth exactly.
- **`config.GENETIC_DATATYPE_ID = "genetic_association"`** is the only new constant — a real OTP schema-level identifier, the same for every disease, not a disease-specific tuning knob (unlike the list it replaces). Wired into both consumers that used to duplicate the hardcoded list: `scripts/ingest_evidence.py`'s `ingest_target()` and `app/agent/investigation_tools.py`'s `search_genetic_evidence()` — both now call the same `get_evidence_by_datatype()`, no duplicated fetch logic.
- **A second, previously-unknown bug surfaced and got fixed as a side effect:** the old per-datasource loop capped each individual datasource at `size=200` (the old default). SOD1's real `eva` count is 275 — the old code was silently truncating 75 real rows on top of missing `orphanet` entirely. The new fetch is paginated with no cap.

### Phase 10 follow-up: read/write separation (GET vs. POST) ✅ DONE
Fixes the architectural gap named above: the API had only POST endpoints for scores/contradictions/gaps, each of which actively recomputes AND persists a new result every time it's called — "viewing" a target and "recomputing" it were the same action. Added real, separate GET routes that read the latest persisted result without recomputing anything; POST endpoints are unchanged and still exist, now conceptually reserved for an explicit future "recompute" action.

**New routes:**
- **`GET /scoring/target/{id}`** — latest `PriorityScore` by `computed_at` descending; 404 if none exists yet. A score is never legitimately "empty" the way a contradiction/gap list can be, so 404-vs-200 is the only distinction needed here.
- **`GET /contradictions/target/{id}`** — every persisted `ContradictionLog` row (both `structured_classifier`- and `llm_proposer`-sourced), no recomputation.
- **`GET /gaps/target/{id}`** — current `GapRecord` rows, same `GapAnalysisOut` shape as the POST route (`investigation_coverage` is recomputed inline since it's a pure, always-"complete" function of `MVP_DIMENSIONS` for the fixed pipeline — not a stored value, so nothing to read-vs-recompute here).

**The real ambiguity the task asked me to consider, resolved with a new table, not a heuristic:** an empty `ContradictionLog`/`GapRecord` result is genuinely ambiguous on its own — it could mean "checked, zero found" (the real, common case — e.g. SOD1 has zero real gaps) or "never checked at all". Considered a heuristic proxy (e.g. "does a `PriorityScore` row exist" implies contradictions were probably run) and rejected it — `scoring.py`'s own long-standing docstring already documents that this doesn't reliably hold ("run contradictions first or Consistency will read as 1.0 — no logged conflicts != no possible conflicts"). Added a small, explicit new table instead: **`PipelineRunLog(target_id, stage, run_at)`** — one row inserted every time `POST /contradictions/target/{id}/run`, `.../run-literature`, or `POST /gaps/target/{id}/run` succeeds. The GET routes 404 with a clear message if no row exists for that target+stage, and return the real (possibly empty) persisted result otherwise. Migrated via `scripts/migrate_add_pipeline_run_log.py` — a new table (`Base.metadata.create_all()` handles this natively, no `ALTER TABLE` needed) — and **backfilled with 10 real rows** (5 targets × 2 stages), since all 5 candidate targets genuinely have had both stages run against them multiple times across earlier phases of this project; backfilling known real history, not fabricating it, same principle as Phase 7's `proposed_by` backfill. DB integrity confirmed after migration (2,292 evidence records, 5 targets, unchanged).

**Real, DB-level proof these GET routes don't mutate anything** (not just asserted): queried `PriorityScore`/`GapRecord`/`ContradictionLog` row counts directly before and after issuing 3 consecutive GET calls to each new route — row counts were bit-for-bit identical in every case (SOD1's `PriorityScore` count: 15 before, 15 after; C9orf72's `GapRecord`: 3/3, `ContradictionLog`: 0/0).

**Frontend (`api.ts`) rewritten to use GET exclusively for display — a real, larger consequence surfaced while doing this, reported rather than silently absorbed:** the previous version deliberately ran the structured contradiction check on every list load AND ran the real, LLM-backed literature check (`POST .../run-literature`) every time a target's detail page opened — a genuine Groq API cost paid on a passive page view, i.e. exactly the same "viewing == recomputing" bug this task fixes, just at a different endpoint. Removing ALL automatic POST calls from passive loads (per the explicit instruction) necessarily removes that literature POST call too — so `TargetList` and `TargetDetail` now read `GET /contradictions/target/{id}` (which returns both classifications together), fetch identically, and neither triggers any LLM call anymore. `fetchTargetSummaries()` and `fetchTargetDetail()` now share one `buildTarget()` helper.

**This makes item 5's original premise ("list view is structured-only, detail page also checks literature") stale, not just the wording — flagged rather than silently kept:** that asymmetry existed ONLY because computing (POST) the literature check was expensive; reading (GET) whatever's already persisted costs the same regardless of source, so there's no remaining reason to treat list vs. detail differently. The requested indicator was added to `TargetList.tsx` (a real footnote below the legend, not just documented here), but reworded to state the actual current behavior honestly: flags reflect each target's most recently checked/computed results (including any literature contradictions already found), are read-only, and are not silently re-checked — rather than repeating a distinction that would now be inaccurate. `TargetDetail.tsx`'s "Checking literature for contradictions (real LLM call)…" indicator (added in the prior turn) was corrected to "Refreshing…", since re-opening a target now just re-reads the same real data, no LLM call involved.
